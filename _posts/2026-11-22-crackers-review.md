한 줄 요약: **Ghidra의 중간 언어 p-code로 "하고 싶은 동작"을 적으면, SAT/SMT 솔버가 바이너리 속 가젯을 조합해 그 동작을 흉내 내는 ROP 체인을 자동으로 찾아 준다. 특정 아키텍처에 묶이지 않으면서 기존 도구보다 빠르고 성공률도 높다.**

---

## 읽기 전에 — 세 가지 질문

- **이 논문이 다루는 문제는?** 코드 재사용 공격(ROP)의 체인을 자동으로 합성하는 문제.
- **왜 중요한가?** 기존에 체인을 사람이 손으로 짜는 것은 힘들었다. 자동화되면 방어 측에선 "이 바이너리로 공격이 실제로 가능한가"를 대규모로 측정할 수 있다.
- **기존 방식은 뭐가 부족했나?** 가젯을 정해진 템플릿이나 기능 범주에 억지로 끼워 맞추거나, 문제 전체를 하나의 거대한 식으로 풀어서 느렸다.

---

## 기 — 배경과 문제 정의

### 코드 재사용 공격이 나온 흐름

공격과 방어는 계속 서로를 밀어내며 발전해 왔다.

1. **코드 주입:** 예전엔 버퍼 오버플로로 스택에 직접 만든 코드를 올리고 그리로 실행 흐름을 돌렸다.
2. **W⊕X(NX)의 등장:** "쓸 수 있는 메모리는 실행 못 한다"는 규칙이 걸리면서, 주입한 코드가 실행되지 않게 됐다.
3. **코드 재사용(ROP):** 그러자 공격은 "새 코드를 못 넣으면, 이미 실행 권한이 있는 코드를 재사용하자"로 바뀐다. 프로그램 안에 있는 짧은 조각(가젯)을 이어 붙여 원하는 동작을 조립한다.
4. **ASLR의 등장:** 주소를 매번 랜덤 배치해 가젯 위치를 못 맞추게 한다. 하지만 정보 노출 취약점과 결합하면 이 방어 아래서도 ROP는 여전히 가능하다.

### ROP 자동화가 필요한 이유

ROP 체인을 만들려면 "어떤 가젯을, 어떤 순서로 이어야 원하는 상태가 나오는가"를 풀어야 한다. 이건 바이너리마다, 아키텍처마다 새로 해야 하는 작업이다. 사람이 반복하기엔 비싸고, 그래서 자동화 연구가 꾸준히 있었다.

### 기존 도구들의 한계

- **ROPGadget, Ropper:** 정해진 템플릿 모양의 가젯을 찾아 미리 짜둔 배치에 끼워 넣는다 → 특정 체인만, 유연성 낮음.
- **angrop, ROPium:** 가젯을 같은 기능 범주로 분류한다 → 한 가젯이 여러 일을 하거나 지저분하면 버려져서, 가젯이 적은 환경에서 약하다.
- **SGC:** 문제 전체를 하나의 거대한 SMT 식으로 표현한다 → 표현력은 좋지만 문제가 커지면 급격히 느려진다.

## 승 — 핵심 아이디어

### p-code로 추상화

crackers는 기계어를 Ghidra의 중간 언어 p-code로 번역해 다룬다. p-code는 모든 아키텍처의 명령어를 담는 공통 표현이라, 한 번 지원하면 SLEIGH가 지원하는 30개 이상 아키텍처에 그대로 적용된다. 또 p-code 연산은 자기가 읽고 쓰는 부분(varnode)을 빠짐없이 명시하기 때문에, 숨은 부작용 없이 논리식으로 깔끔하게 모델링할 수 있다. 이 성질 덕분에 가젯을 기능 범주로 분류하지 않아도 된다.

### SAT / SMT 분리

crackers는 문제를 두 솔버로 나눠 푼다.

- **SAT 솔버:** 각 단계 선택을 불리언 변수로 만들어 체인 후보를 뽑아준다. 가볍고 빠르다.
- **SMT 솔버(Z3):** SAT가 찾아준 조합이 실제로 실행되었을 때, 레지스터, 메모리가 원하는대로 나오는지 검증한다.
- 검증이 실패하면 원인을 분석해 충돌 절(conflict clause)을 만든다. 같은 실수를 반복하지 않게 한다.

SGC가 모든 걸 하나의 SMT 식으로 밀어 넣어 느렸던 것과 달리, 분리를 통해서 crackers가 빠른 속도를 낼 수 있게 한다.

## 방법론 / 시스템 구성

### p-code의 형식 모델 (3장)

p-code를 솔버가 다룰 수 있는 논리로 번역하는 규칙을 세운다.

- **상태:** 주소공간을 "주소 → 값" 배열로 보고 SMT의 배열 이론(ArraysEx)으로, 값은 비트벡터 이론(FixedSizeBitVectors)으로 표현한다. 읽기는 `select`, 쓰기는 `store`. 레지스터든 메모리든 전부 같은 방식이라 아키텍처 가정이 필요 없다.
- **연산:** 각 연산을 "실행 전 상태 ↔ 실행 후 상태"의 논리적 관계로 표현하고, 이어 붙여 블록 전체의 의미를 만든다.
- **제어흐름:** "이 블록이 어디로 점프하나"를 대상 주소 비트벡터로 표현한다. 조건부 분기는 다루지 않고, 단일 기본 블록만 대상으로 한다.

### 합성 알고리즘 crackers (4장)

대략 이런 순서로 돈다.

1. **가젯 라이브러리 생성:** 바이너리의 실행 영역을 훑어 간접 분기로 끝나는, 모델이 다룰 수 있는 블록만 가젯으로 모은다.
2. **참조 프로그램 분해:** 원하는 동작을 단계 시퀀스로 나눈다. 더 짧은 체인을 먼저 시도하도록 분할을 길이순으로 본다.
3. **가젯 후보 식별:** 각 단계가 바꾸는 출력을 가젯이 덮는지 구문적으로 걸러 후보 풀을 만든다.
4. **체인 선택(SAT) → 검증(SMT):** SAT로 조합을 뽑고 SMT로 검증한다. 실패하면 충돌 절로 탐색을 좁힌다.
5. 성공하면 체인 반환, 모든 분할이 실패하면 실패.

## 전 — 실험과 결과

### 평가 설정

ALLSTAR(Debian) 데이터셋의 x86-64 바이너리 1000개를 대상으로, 함수 호출을 수행하는 체인 합성을 각 도구에 시켰다. 도구당 바이너리마다 30분 타임아웃.

### 기존 도구와의 비교

성공률에서 crackers가 크게 앞섰다.

| 도구 | 성공률 |
|---|---|
| crackers | 92.4% |
| SGC | 52.7% |
| exrop | 34.6% |
| angrop | 25.4% |

속도(실행 공간 1KB당 합성 시간, TkB) 기준으로도 crackers가 가장 빨랐다. SGC는 표현력은 비슷하지만 가장 느렸다.

### 제거 연구 (Ablation)

핵심 요소를 하나씩 빼 보며 영향을 측정했다. 특히 **참조 프로그램을 제거한 변형(crackers_b)**은 타임아웃이 약 80%까지 치솟아 성능이 크게 무너졌다. 참조 프로그램이 성능의 핵심임을 보여 주는 결과다. 충돌 절 약화 휴리스틱(crackers_a)은 효과가 더 미묘해서, 선택적 요소로 남겨 둘 만하다는 결론이다.

### 실전 사용례 (CVE)

공개된 실제 취약점(dnsmasq의 CVE-2017-14493)을 대상으로, 실제 익스플로잇 상황에서 오는 복잡한 제약을 걸고 동작하는 체인을 합성하는 데 성공했다. 이런 세밀한 제약은 다른 ROP 합성 도구로는 표현하기 어렵거나 불가능하다는 점을 저자들은 강조한다.

## 한계점 및 아쉬운 점

- 조건부 제어흐름(CBRANCH)과 루프를 다루지 않고, 단일 기본 블록만 지원한다.
- 부동소수점 연산을 다루지 않는다.
- 시스템 콜을 표현하는 CALLOTHER 지원이 제한적이다.
- 비교 평가가 현실적 상태 제약 없이 돌아서, 의미상으론 가능하지만 실제 익스플로잇에선 도달 불가한 체인을 성공으로 셌을 가능성이 있다(저자도 한계로 인정).

## 결 — 느낀 점과 앞으로

### 내가 느낀 점 / 배운 점

> 혼자 보안공부를 하며, ROP에 대해 본적이 있었다. 당시에는, 시험 공부에 우선 순위가 밀려서 다음에 공부해야지 하고 넘어 갔던 개념이었다.
> 이번에 논문 리뷰를 하며, 가장 인상 깊었던 점은 p-code라는 추상화였다. p-code로 잘게 쪼개서 나타내면, 효과를 숨기지 않게 되므로, 솔버가 자동으로 추론할 수 있는 기반이 된다는게 신기했다. 

### 이어서 해볼 만한 방향

- **더 읽어볼 논문:** 비교 대상이던 SGC(Schloegel et al., ESORICS '21), 그리고 ROP의 출발점인 Shacham의 원 논문.
- **다른 분야 적용:** 같은 "참조 프로그램 → 솔버 합성" 틀을 펌웨어/IoT 바이너리나 다른 아키텍처(ARM, MIPS)에 적용해 보기.
- **직접 재현/비교:** 공개된 아티팩트(Zenodo)로 crackers를 돌려 보고, 내가 워게임에서 손으로 짠 체인과 비교해 보기.
- **연구/프로젝트로 발전:** 저자들이 제시한 "자연어 사양 → LLM → 참조 프로그램" 방향을 더 파 보거나, 조건부 분기 지원 같은 한계를 메우는 쪽.
